## F01 — webhook receipt can suppress recovery after processing failure

**Confirmed live at baseline**, not already fixed. Read `apps/api/src/routes/webhooks/shopify.ts`'s `recordDelivery` (now `claimDelivery`) directly:

- The delivery-dedup row (`shopify_webhook_deliveries`, keyed on `(connection_id, webhook_id)`) was inserted **before** the business transaction ran.
- On Shopify's automatic redelivery (same webhook id), the old code hit the unique-constraint violation and returned `false` — the caller (`/orders-create` and all four other handlers sharing this function) treated that as `alreadyProcessed: true` and returned **immediately, before ever checking whether the actual order/customer/inventory effect had completed**.
- Any failure between the delivery insert and the transaction committing — a crash, a DB timeout, an unrelated exception, anything other than the orders-table's own `(org_id, shopify_order_id)` unique-constraint race (which *was* already handled) — left a permanently "already processed" delivery row next to a business effect that never happened. The order was lost silently; Shopify saw 200 and stopped retrying.
- The schema already had `status` (default `'received'`), `error`, and `processedAt` columns on this exact table — designed for a lifecycle that nothing ever read or wrote.

**Fix**: `claimDelivery` now looks up the *existing row's status* on a redelivery instead of assuming existence means success. Only `status === 'processed'` short-circuits as already-done; `'received'`/`'failed'` return `{ kind: 'retry' }`, which the caller must reprocess (reusing the same delivery row, not losing it). `markDeliveryProcessed` is called **inside the same database transaction** as the order-creation/stock-decrement effect for `/orders-create` (and the restock effect for `/orders-cancelled`) — both commit together or neither does. The three lower-risk handlers (`/orders-updated`, `/customers-upsert`, `/inventory-levels-update`) mark processed just after their own naturally-idempotent single-statement effect commits; a small window there is acceptable since retrying any of them is itself a safe no-op (unlike order creation, which is not naturally re-runnable without this fix).

**Acceptance (A01)** — "crash after webhook reception... retry the same delivery ID... exactly one order... eventually processed": proven at the decision-logic level by `shopifyWebhookDeliveryLifecycle.test.ts`'s `'THE F01 REGRESSION'` test, which reproduces the exact prior-crash state (a `'received'`-status row with no completed effect) and asserts the redelivery is claimed as `'retry'`, not `'processed'`. Full end-to-end proof (an actual crash mid-transaction against real Postgres) is not covered here — see BASELINE.md's testing-infrastructure limitation.

**Files changed**: `apps/api/src/routes/webhooks/shopify.ts` (all 5 webhook handlers), new test file, one sibling test file's mock corrected. No schema migration — the lifecycle columns already existed.

**Process note**: the first implementation attempt built this fix on a local working copy of `shopify.ts` that was 8 commits behind `origin/main`. One of the missing commits had already landed an unrelated but important fix in the same file — sorted line-item locking plus a `.for('update')` fallback, preventing cross-request deadlocks on shared inventory rows. Copying the stale edit into a fresh PR branch silently reverted that fix. `shopifyLockOrderGate.test.ts` — a static source-text gate written specifically to catch this class of regression — failed in CI and caught it before merge. The fix was rebuilt directly against the real current file (`git show origin/main:<path>`, diffed against the committed change before reapplying) rather than the stale local copy; all three previously-failing test files were individually confirmed green in the CI log (not just the job-level pass) before merging. Lesson applied going forward: always diff a to-be-edited file against real `origin/main` before trusting a local scratch copy, given other concurrent work in this repo's shared scratch worktree.

## F02 — concurrent order-status transitions can duplicate revenue

**Confirmed live at baseline.** All three status-transition entry points (admin `updateStatus` mutation, apps/api PATCH `/:id/status`, the Bosta courier webhook) read the order's current status in one step, then decided in a separate step whether to post a delivery ledger entry / send a notification, then wrote the new status. Two callers racing on the same order — an admin double-click, admin and the Bosta webhook landing near-simultaneously, or a retried webhook delivery — could each read the pre-transition status, each independently decide "not yet delivered," and each post: duplicate `SALES_REVENUE` credit lines for one real delivery event.

**Fix**: `transitionOrderStatus` (`packages/db/src/orderLedger.ts`) reuses F01's atomic locked-transition pattern — a single `UPDATE ... FROM (SELECT ... FOR UPDATE)` CTE that serializes concurrent callers on the row lock and returns the row's true previous status to whichever caller performed the write, not a separately-read stale value. All three entry points now key their ledger/notification/audit-log logic off that returned value.

**Acceptance**: proven directly against real Postgres — `idempotency.test.ts`'s new integration test fires 20 concurrent `transitionOrderStatus`+`postOrderDeliveredEntry` calls at one order and asserts exactly one delivery-transition winner, zero duplicate journal entries, and zero rejections. This is the one F02 acceptance criterion that could not be proven at the mocked-unit level and needed CI's real database.

**Files changed**: `packages/db/src/orderLedger.ts`, `apps/admin/src/server/routers/orders.ts`, `apps/api/src/routes/orders.ts`, `apps/api/src/routes/webhooks/bosta.ts`, plus test files in both apps. No schema migration.

**Explicitly out of scope**: order-status state-machine validation (which transitions are valid vs. rejected as invalid backwards moves) — needs a business decision on the transition graph, not made yet.

**Process note**: implemented via the `codex-delegate` skill (Codex/OpenAI CLI as implementer). Two environment blockers surfaced before a run completed — the initially-requested model was too new for the installed CLI version (resolved by the user upgrading the CLI), and a `lean-ctx` tool-approval deadlock combined with a Windows sandbox permission wall blocked both dispatch attempts under `workspace-write` (resolved by dispatching under `--sandbox danger-full-access`). One scope-correction was needed on review: Codex's first pass added new apps/api- and Bosta-specific test coverage inside admin's test file to avoid touching files outside the brief's list, violating this repo's one-app-tests-its-own-routes convention. Sent as a scoped delta brief on the same Codex session (`--session <threadId>`) rather than a full re-brief; the correction was independently re-verified (both relocated test files use their destination file's own native mocking conventions, admin's test file no longer references `apps/api`) before landing.

## F03/F04 — return creation omits original order-line linkage; return restocking races and omits cost reversal

**Confirmed live at baseline, both defects.** `returns.create` took free-typed `productName`/`variantName`/`quantity`/`unitPrice` strings with zero reference to the order's actual line items — `returnItems.orderItemId` already existed in the schema (nullable, no FK) but nothing ever set it. `returns.restock`'s existence/idempotency pre-checks ran as plain reads before the transaction, then the transaction unconditionally flipped the restock flag — two concurrent calls for the same item could both pass the stale check and both perform the physical/financial effects twice. restock also posted **zero** cost reversal: a delivered item's cost basis (`orderItems.costMinor`) was expensed to COGS at delivery and never reversed on return, and every returned item — including damaged ones — was unconditionally restocked as saleable.

**Fix**: `create` now requires `orderItemId` + `quantity` + optional `condition`; derives product/variant/price server-side from the real joined rows, verifies the line belongs to the given order and org, and bounds cumulative returns against the order line's own quantity — each referenced line locked in **sorted id order** (reusing this repo's own lock-ordering idiom from the Shopify webhook fix) to avoid deadlocking overlapping multi-line requests. Adds the missing FK. `restock`'s claim is now a single conditional `UPDATE ... WHERE restock = false RETURNING` inside the transaction — only the caller that wins the row proceeds. Posts `INVENTORY` debit / `COGS` credit for the original cost × quantity when a cost basis is known. Only `'new'`/`'good'` condition increments saleable `inventoryItems.quantity`; `'damaged'`/`'unknown'` holds stock out of saleable inventory (still logged for audit) since no quarantine/multi-location model exists yet — the financial reversal applies either way.

**Acceptance**: proven directly against real Postgres — `returnsRestock.test.ts`'s new integration test fires 10 concurrent `restock` calls at one return item and asserts exactly one winner, inventory incremented by exactly one item's worth (not accumulated across calls), and exactly one journal entry with the correct INVENTORY/COGS lines.

**Files changed**: `apps/admin/src/server/routers/returns.ts`, `packages/db/src/schema/returns.ts`, new migration `0053_return_items_order_item_fk.sql`, plus test files. Nothing in the admin UI calls `returns.create` yet, so tightening its input contract broke no existing screen.

**Explicitly out of scope**: return-status state-machine validation, a quarantine/multi-location inventory model, new frontend UI.

**Process note**: implemented via the `codex-delegate` skill. The account's Codex usage limit was hit and reset three separate times across this fix's dispatch — each retry made real progress before dying mid-turn with no self-report, so every stage was reviewed from the diff directly rather than trusting a report that didn't exist. The first full run was correct in its core logic (atomic claim, cost reversal, disposition split, sorted lock ordering) but had two gaps found on my own review: a corrupted em-dash character (mojibake) in two description/note strings, and the required real-Postgres concurrency test was missing — both were sent as one scoped delta brief on the same Codex session and closed correctly. Two further defects surfaced only after Codex's involvement ended (found and fixed directly, not delegated): (1) a pre-existing test file, `moneyPathIdempotency.test.ts` — not in any brief's file list, undiscovered by Codex — asserted the *old* restock mechanism ("the idempotency guard must short-circuit before entering the transaction at all") as an invariant; the new atomic claim correctly requires entering the transaction to attempt the claim, so that assertion is now testing against the very race this fix closes. Rewrote it to assert what actually matters (no duplicate physical/financial effects on a second call), not the old mechanism. (2) The new FK migration's bare `ADD CONSTRAINT` failed in CI's real-Postgres integration job — rewritten idempotent (drop-then-add) per migration `0052`'s own documented convention for exactly this class of DDL, rather than a `DO`-block existence check, matching established precedent instead of inventing a new pattern.

## F08 — legacy Shopify fallback is insufficiently scoped

**Confirmed live at baseline, both directions.** `resolveWebhookOrg` (inbound webhooks) fell back to the legacy single-tenant `SHOPIFY_ORG_ID` whenever a shop domain had no *matching active* connection — covering both "header genuinely absent" (the intended legacy path) and "known-but-uninstalled or unknown shop" (should fail closed, didn't). The only prior test covered "unmatched domain + no legacy org configured" — not "unmatched domain + legacy org **is** configured," which is the actual live-risk case (the env var is set in production today). The outbound `shopify.product.push` outbox handler had the same shape: any org with no active connection of its own — not just the one org `SHOPIFY_ORG_ID` names — fell back to the legacy global Shopify client, silently pushing into someone else's shop.

**Fix**: `resolveWebhookOrg` now only reaches the legacy fallback when the `X-Shopify-Shop-Domain` header is genuinely absent; a supplied domain matching no active connection now returns `null` (fails closed). The outbox handler now refuses the legacy-client fallback unless `orgId` exactly matches `SHOPIFY_ORG_ID`, throwing a descriptive error that reuses the existing `attempts`/`lastError` dead-letter machinery instead of silently misrouting.

**Acceptance**: `shopifyWebhookOrgResolution.test.ts` (extended) and new `shopifyOutboxLegacyFallback.test.ts` cover both directions with `SHOPIFY_ORG_ID` configured — the scenario the prior suite missed.

**Files changed**: `apps/api/src/routes/webhooks/shopify.ts`, `apps/api/src/workers/outboxWorker.ts`, plus test files. No schema/migration change.

**Process note**: implemented via the `codex-delegate` skill; the dispatch that produced this fix hit the account's usage limit mid-turn before Codex could self-report, so this PR is the product of an independent line-by-line diff review rather than a verified self-report — found correct and complete as delivered, no delta brief needed. No local gate re-run was possible in this worktree (no local install attempted); CI's fresh install, including the `test` job, was the real verification.

## F06 — document currency is not propagated into ledger lines

**Confirmed live at baseline.** Dashboard- and API-created orders both hardcode `EGP` explicitly — no live risk there. The real gap: the Shopify webhook's `orders-create` handler took `payload.currency` — genuinely external, provider-controlled input — and wrote it straight onto the new order with no validation it's a currency this system actually supports. Separately, `packages/db/src/ledger.ts`'s `postJournalEntry` had no `currency` field on its input contract at all — every journal line ever posted silently took the `journal_lines.currency` column's bare `'EGP'` database default, regardless of the source document's real currency; `orderLedger.ts` validated a currency for arithmetic but never passed it through to the actual posting.

**Fix**: added `assertSupportedCurrency` (packages/domain) — a real allowlist check (`['EGP']` today, matching the recorded Phase 0 EGP-primary baseline decision), distinct from the existing `currency()` format-only parser. `JournalLineInput.currency` is now required and enforced/persisted by `postJournalEntry`, including a same-currency-across-all-lines guard. Every current `postJournalEntry` caller (`orderLedger.ts`, `returns.ts`'s refund and cost-reversal postings, `purchasing.ts`, plus `giftCards.ts`/`stocktaking.ts`/`courier.ts` with honest provisional EGP defaults where no real currency source exists yet) traces its real currency through. The Shopify webhook now rejects/quarantines an unsupported-currency order before it's ever created, reusing F01's `markDeliveryFailed` pattern, returning 200 so Shopify doesn't retry a permanently-unsupported case.

**Explicitly out of scope**: full FX/multi-currency support, a currency picker UI.

**Process note**: implemented via Jules (Google's async coding agent, API-driven, `requirePlanApproval` used for a pre-execution review checkpoint). The generated plan initially proposed a check-then-insert idempotency pattern elsewhere unrelated to this fix's scope — not applicable here, no delta needed for F06's own plan. One real scope conflict caught in plan review: the plan listed `purchasing.ts` as a file to touch, which collided with the original brief's "out of scope: purchasing.ts" note — clarified that the note meant F13's actual PO-completion logic, not the mechanical touch every `postJournalEntry` caller now needs; the implementer correctly traced `purchasing.ts`'s own real `po.currency` once clarified, rather than a lazy default. ## F09 — Paymob callback lacks a complete payment lifecycle

**Confirmed live at baseline** (a scoped first pass, not the full payment-lifecycle rebuild the broader plan eventually calls for). The Paymob webhook had no idempotency at all — a replayed callback re-ran the same unconditional status write every time. It never compared `obj.amount_cents`/`obj.currency` against the order's own total/currency before confirming. It collapsed Paymob's actual lifecycle fields (`pending`, `is_refunded`, `is_voided` — already read into the HMAC check, never inspected for meaning) into a binary success/fail, so a refund or pending-transaction callback could have been treated as a fresh successful payment. And it wrote `orders.status` — the same column F02's `transitionOrderStatus` manages atomically elsewhere — via a bare, unguarded `UPDATE`.

**Fix**: a new `paymob_webhook_deliveries` table dedupes on `(org_id, transaction_id)` via insert-then-catch-23505 (F01's `claimDelivery` pattern, not a racy check-then-insert). Amount/currency are compared exactly (BigInt, not lossy string-of-float) before any effect. Only `success === true && !pending && !is_refunded && !is_voided` with a matching amount/currency is treated as a genuine capture. `transitionOrderStatus` gained a new optional `onlyIfPreviousStatusIn` parameter — folded into the same atomic `UPDATE`'s `WHERE` clause, not a separate racy pre-check — so this webhook can only transition an order forward from `'pending'`/`'payment_failed'`, never regressing one already `confirmed`/`shipped`/`delivered`/`cancelled`; the three existing callers are unaffected since the parameter is optional.

**Explicitly out of scope**: a full payments/paymentAttempts subledger modeling every provider state, real refund processing, settlement reconciliation, Paymob checkout/intention creation (nothing creates one yet).

**Process note**: implemented via Jules, with two rounds of plan-review correction before execution — (1) the first plan proposed check-then-insert for delivery dedup (the exact race class F01/F02/F04 already closed elsewhere in this codebase) and left `transitionOrderStatus`'s non-regression guard as a vague "don't override" with no atomic mechanism specified; both were corrected before approval (unique-constraint-plus-catch, and an atomic WHERE-clause parameter) and the revised plan implemented both correctly. (2) Mid-execution, the implementer hit a self-inflicted syntax mess trying to patch an existing test file via scripted search/replace and asked whether to rewrite it from scratch — approved.

Post-completion, full diff review before merge found three further issues the implementer's own report didn't surface: a deep `@irth/db/src/orderLedger` import inconsistent with every other caller in this codebase (fixed to the standard `@irth/db` import); the amount check compared `String(obj.amount_cents)` against `String(order.totalAmountMinor)` — a JSON float against an exact bigint, incidentally correct only for small values (fixed to an exact `BigInt()` comparison); and the from-scratch test rewrite had silently dropped an existing, valuable regression test for a *different*, previously-fixed vulnerability (cross-tenant order lookup via `orderNumber` instead of `orders.id`) — restored it. All three were fixed directly on the PR branch rather than re-delegated, since the session had already completed.

CI then caught a fourth, more serious issue neither the implementer nor the initial review surfaced: the new `paymob_webhook_deliveries` table (which stores full Paymob payloads, including card metadata under `source_data`) was created with no Row-Level Security — the exact recurring defect this repo's own migration history (0049/0050/0052) already hit and fixed for seven other tables. Added `0055_paymob_webhook_deliveries_rls.sql` following that established pattern exactly, traced safe (the table's only reader/writer already bypasses RLS via the owner-role `db`, so no existing behavior changes).
