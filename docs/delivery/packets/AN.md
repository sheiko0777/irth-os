## Decisions
- **Storefront capture on Shopify** → Shopify Web Pixel APP EXTENSION (strict sandbox, web worker) subscribing to the 13 standard customer events; batch-POST to the Worker /collect with fetch keepalive. No DOM, no web-vitals, no scraping from the pixel. Consent is declared in shopify.extension.toml (customer_privacy: analytics=true only) so Shopify's pixel manager loads the pixel only when the visitor has granted analytics permission; consent state is also read from init.customerPrivacy + visitorConsentCollected and stamped on every event.  
  _Verified on shopify.dev: app-extension pixels run in a 'strict' sandbox (only self/console/timers/fetch guaranteed; window.document unavailable); 'Shopify's pixel manager will only load your pixel if there is visitor permission for all of the settings that your pixel declares as required'; pixels can 'securely access all surfaces, like storefront, checkout and post-purchase pages'; the browser API (cookie/localStorage/sessionStorage) is async-only. This is the only way to see checkout events on non-Plus stores. The existing apps/api/src/routes/shopifyPixel.ts already assumed this model (its own header says the extension 'is explicitly out of scope') — we now build the missing half._ [all_agree] — https://shopify.dev/docs/apps/build/marketing-analytics/pixels ; https://shopify.dev/docs/api/web-pixels-api/pixel-privacy ; https://shopify.dev/docs/api/web-pixels-api/standard-events ; https://shopify.dev/docs/api/web-pixels-api/standard-api/browser ; apps/api/src/routes/shopifyPixel.ts lines 9-12
- **Storefront capture on WooCommerce / other domains** → One PHP mu-plugin per Woo site that (a) sets a first-party HttpOnly anonymous-id cookie server-side, (b) enqueues the shared JS collector (same versioned schema), (c) surfaces product/cart/checkout/thank-you facts from WC template hooks to the JS layer, (d) optionally posts checkout_completed server-side with the same event_id for reliability, (e) gates on a consent filter. No GA4, no Woo analytics namespace.  
  _Woo has no first-party pixel; a mu-plugin cannot be deactivated by mistake and can set HttpOnly cookies (which browser JS cannot). Same schema means one collector, one storage, one funnel report._ [all_agree] — astra §C table row 'WooCommerce behavior'; synthesis module connector-woocommerce
- **Event schema** → One versioned Zod schema in packages/domain: envelope {v:1, event_id, site_key, event_name, occurred_at, anonymous_id, session_id, consent{analytics,marketing,preferences,sale_of_data}, page{path,referrer_host,utm_*}, device{class}, props}. Event names = Shopify standard taxonomy verbatim (page_viewed … checkout_completed) + web_vital. No Segment-style identify/track/page layer. PII fields (email/phone/name/address) are rejected by the schema, not just ignored. Browser purchase events NEVER create revenue; they carry order_ref/checkout_token for matching only.  
  _Shopify already defines the names and payload shapes; inventing a second taxonomy adds a mapping layer for zero benefit. Astra's 'short event list' + 'Browser purchase events never create financial revenue' are both honoured structurally._ [astra_overrides] — astra §C ('Capture a short event list…', 'never add their purchase totals together'); synthesis events-pipeline proposed Segment-shaped track/identify/page — dropped as an extra layer
- **Collector** → POST /collect/:siteKey on apps/api (Hono). Site key resolves a channel (CX channels/connections row) — same 404-shape-for-unknown as the current pixel route; body ≤32 KB, ≤50 events; Zod validation; clock-skew window (−7d…+5min); per-IP rateLimit (existing middleware); CORS restricted to the channel's configured storefront origins; bot UA denylist; consent.analytics=false → 204 drop; the only DB touch in the request path is a cached key lookup. 202 is returned only after the Queue send() resolves.  
  _A DB outage must not hold open browser requests or flood the OLTP DB (astra). The current shopifyPixel.ts does two synchronous inserts per event on the owner role — cut._ [all_agree] — astra §C 'Choose Queues rather than direct event inserts…acknowledge the collector only after durable enqueue'; apps/api/src/middlewares/rateLimit.ts; apps/api/src/routes/shopifyPixel.ts
- **Transport: Cloudflare Queue + DLQ** → One queue irth-events (producer = /collect, consumer = the same Worker's queue() handler), one DLQ irth-events-dlq. Consumer: max_batch_size 100, max_batch_timeout 30 s, max_retries 5, max_concurrency 2 (bounded to protect Neon). One queue message = one collector request (N events), not one message per event. Bindings must be repeated under [env.production] and [env.staging] (wrangler.toml already documents that named envs do not inherit bindings).  
  _Verified pricing: Workers Paid includes 1,000,000 operations/month then $0.40 per million; an operation is counted per 64 KB written/read/deleted, so a delivered message costs 3 ops and each retry +1. Batching ~5 events per message at 2M events/month ≈ 1.2M ops ≈ $0.08/month. Workers Free allows only 10,000 ops/day with 24 h retention — too small for peaks, so Workers Paid is assumed (open question). Verified limits: message 128 KB, batch 100 messages, batch wait 60 s, retention 4 d default/14 d max, retries 100, consumer concurrency 250, sendBatch 100 msgs/256 KB, 5,000 msg/s, consumer wall-clock 15 min._ [all_agree] — https://developers.cloudflare.com/queues/platform/pricing/ ; https://developers.cloudflare.com/queues/platform/limits/ ; apps/api/wrangler.toml (R2 binding comment on env inheritance)
