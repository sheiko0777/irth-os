# reconcile:CX: CX — Connectors, adapters, public API, MCP, auth, roles, approvals, audit, security

## Decisions
- **Operation functions as the single source (no op-registry generator)** → Business logic lives in ordinary TS functions `(tx, input) => output` under packages/db/src/ops/<module>.ts, each exporting its zod input/output schema next to it (the pattern packages/db already uses for postJournalEntry / transitionOrderStatus / recordCostedReceipt). tRPC procedures (admin, kept), Hono REST routes (S5 public API via @hono/zod-openapi) and MCP tools (S5, hand-curated) are one-line callers. No code generator, no registry object that emits four surfaces. A grep-style gate (same shape as apps/admin/src/__tests__/tenancyGate.test.ts) fails the build when a router/route file contains a Drizzle write outside a baseline list.  
  _Astra A explicitly cut the universal generator; the existing kernel already proves the 'transactional function in packages/db, thin caller elsewhere' pattern works and is testable against real Postgres. tRPC stays because 28 routers + 46 screens + router tests exist and rewriting them to REST is not a business transaction._ [astra_overrides] — packages/db/src/ledger.ts, packages/db/src/orderLedger.ts, apps/admin/src/server/trpc.ts (withOrg/idempotent plumbing kept); astra A table row 'Registry generating tRPC, REST, MCP…'
- **Adapter interfaces with static manifests (no capability router, no providers table)** → Four TS interfaces in apps/api/src/integrations/kernel/types.ts: StorefrontAdapter {fetchOrder (11 parity sections, each tagged loaded|not_applicable|not_exposed_by_provider|permission_denied|fetch_failed), listOrdersSince, publishAvailability (absolute quantities), updateFulfillment, verifyWebhook, parseWebhook, healthCheck}; CourierAdapter {book, cancel, track, importSettlement, verifyWebhook, parseWebhook, healthCheck}; PaymentAdapter {createIntent, capture, refund, importSettlement, verifyWebhook, parseWebhook, healthCheck}; MessagingAdapter {send, listTemplates, verifyWebhook, parseWebhook, healthCheck}. Every adapter exports a static `manifest` (provider slug, family, requiredScopes/credentials, capability booleans, webhook signature recipe, deep-link map of what is deliberately NOT mirrored). Routing is `adapters[connection.provider]` — a Record lookup — after a SQL query on `connections` by (org, family, brand, status, priority). Provider implementation is code; only connections/secrets/config/cursors/health are data.  
  _3 storefronts, 2 couriers, 1 PSP, 1 messaging API do not justify a Nango-shaped providers table or a capability map; astra A said so and the synthesis' capability router was its main over-build. A static manifest still makes vendor-independence real: adding a courier = one folder implementing one interface._ [astra_overrides] — astra A: 'Use explicit adapter interfaces and a small static capability manifest'; synthesis connector-kernel module (cut down)
- **Providers-as-data tables and secret handling** → Two tables (new migration packages/db/drizzle/0067_connections.sql): `connections` (id, org_id, legal_entity_id FK nullable-until-DM-01-lands-then-NOT-NULL-for-storefront/courier/payment, brand_id FK nullable, family enum storefront|courier|payment|messaging|fiscal|mcp, provider text, external_key text (shop domain / account id / phone number id), config jsonb (non-secret: location ids, pickup address, templates, api version, cursors), status enum pending|active|degraded|disabled|uninstalled, health jsonb {checkedAt, overall, sections:{...parity vocabulary}}, cursors jsonb, last_error, last_webhook_at, last_sync_at, timestamps; UNIQUE(org_id, provider, external_key)) and `connection_secrets` (id, org_id, connection_id, name, ciphertext, iv, key_version smallint, expires_at, rotated_at; UNIQUE(connection_id, name)). Encryption = the existing WebCrypto AES-256-GCM code from apps/api/src/services/shopifyConnection.ts generalised into apps/api/src/integrations/kernel/secrets.ts with the KEK read from Worker secrets CONNECTION_SECRETS_KEY_V<n> (wrangler secret put — never in the DB, so never in a Neon backup). Rotation = add V<n+1>, run `rotateConnectionSecrets()` which re-encrypts every row and bumps key_version, then delete V<n>. No per-org DEK envelope. Only kernel/secrets.ts may call decrypt; a gate test asserts no other file imports it.  
  _Ponytail rung 2: the AES-GCM + env-KEK pattern already exists and already satisfies 'keys outside DB backups'; envelope encryption with per-org DEKs adds a key table and wrapping logic for <100 secret rows. key_version gives rotation with one bulk job._ [my_call] — apps/api/src/services/shopifyConnection.ts L16-51 (aesKey/encryptShopifyToken/decryptShopifyToken); wrangler.toml secrets list; astra E 'per-connection encrypted credentials, keys outside database backups, rotation/revocation support'
- **Health checks must test permissions, not HTTP status** → HealthReport = {overall, sections: Record<section, status>, grantedScopes, missingScopes, checkedAt}. Shopify check runs `{ shop { name } }`, reads the access-scope list, then queries one recent order requesting customer/email/phone/shippingAddress; a 200 whose `errors[].extensions.code` is ACCESS_DENIED (or whose customer fields come back null while `customer.id` exists) marks the buyer/addresses sections permission_denied. Bosta/Aramex/Paymob checks call one authenticated read endpoint and classify 401/403 as credentials_invalid. Health is stored on connections.health and rendered on the connections screen; a connection cannot be set 'active' while any required section is permission_denied.  
  _This is exactly the class of failure behind the owner's 'number + price only' order: Shopify redacts protected customer data with a 200. A status-only check reproduces it._ [all_agree] — apps/api/src/services/shopifyConnection.ts shopifyGraphQL L94-105 throws on body.errors — hides which section failed; astra B 'Customer-data permissions must be tested during connector activation'; https://shopify.dev/docs/apps/launch/protected-customer-data

Replaces: shopify_webhook_deliveries, paymob_webhook_deliveries, the two Bosta URLs (/api/webhooks/bosta and /webhooks/bosta), aramex, and the X-Shopify-Shop-Domain + SHOPIFY_ORG_ID tenant resolution.

A connection id in the path plus a per-connection secret makes tenant resolution explicit and secret-bound before any row is written._ [all_agree] — apps/api/src/routes/webhooks/bosta.ts L8-26 (two live Bosta URLs), resolveCourierShipmentByTracking.ts (cross-tenant lookup), webhooks/shopify.ts L85-140 (claim lifecycle worth keeping); astra B ingestion step 1

## Open questions
- Bosta webhook signature and settlement export: is the signature HMAC-SHA256 hex (apps/api/src/routes/webhooks/bosta-webhook.ts) or SHA-512 (routes/webhooks/bosta.ts via verifyHmac)? Does the account expose COD remittance via API or only CSV/Excel from the dashboard? Does booking need Bosta's city/zone ids? — why: Two live files disagree on the algorithm; the courier adapter (CX-14) cannot be finished without the answer, and settlement import shape decides whether COD reconciliation is automatic. — default: SHA-256 hex over raw body (the newer file); settlement = CSV import; address mapping via a config table on the connection.
- Can api.irth-house.com be attached to the Worker (DNS zone in the same Cloudflare account)? — why: Same-site cookies are the simplest way to run ONE Better Auth; otherwise admin must proxy /api/auth/* via Next.js rewrites. — default: Yes — custom domain; fallback rewrites() documented in CX-01.
- Approval thresholds: refund amount and stock-adjustment cost that require approval (EGP), and who approves what (owner only vs admin too; accountant for journals/transfer price). — why: Encoded as org_settings defaults in CX-10 and CX-15; wrong defaults either block ops or leak money. — default: Refund ≥ 1,000 EGP and stock adjustment ≥ 500 EGP cost need approval; owner/admin approve refunds and stock; accountant approves manual journal/reopen and transfer price; supplier bank changes owner-only.
- Shopify Partner-dashboard approvals: request protected customer data access (name/email/phone/address) and read_all_orders now for each store, before S1? — why: Without them the health check will correctly report buyer/addresses = permission_denied and the A4 fixture (if older than 60 days) cannot be fetched. — default: Owner requests both today; S1 fixture must be < 60 days old otherwise.
- WhatsApp provider per brand: keep 360dialog for all three brands or move to Meta Cloud API direct for some? — why: Same MessagingAdapter interface, different manifest/credentials; affects CX-16 and the S5 inbox. — default: 360dialog adapter first; Cloud API adapter added when a brand needs it.
- Which MCP clients will the owner use (Claude Desktop/Code, Codex CLI, ChatGPT) — do they support CIMD or need Dynamic Client Registration? — why: Decides allowDynamicClientRegistration defaults and whether the admin needs a client-approval screen. — default: Enable DCR gated by admin approval + CIMD; owner approves each client once.
- Supplier login method: password + optional TOTP, or OTP/magic link only? — why: CX-20 reuses the invite OTP flow; passwordless is simpler for reluctant suppliers but changes Better Auth config. — default: Invite OTP to set a password; TOTP optional for suppliers.
- Raw webhook body retention period (contains customer PII): 180 days then archive to R2, or shorter? — why: Privacy stance vs replay/dispute needs; encoded in CX-28. — default: 180 days in Postgres, then R2 archive with hash retained; purge R2 after 2 years.
