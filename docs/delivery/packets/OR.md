Pinned version 2025-10 (packages/db/src/shopify.ts) loses support 2026-10-16 — one month from today — so the bump is mandatory, not optional._ [all_agree] — https://shopify.dev/docs/api/usage/versioning (2025-10 accessible until Oct 16 2026; 2026-07 latest stable); https://shopify.dev/docs/api/admin-graphql/latest/objects/Order (lineItems/fulfillmentOrders/discountApplications/shippingLines/events/returns are paginated connections; transactions/refunds/fulfillments/taxLines/discountCodes/tags/customAttributes are plain lists)
- **Protected customer data is the actual cause of 'customer data didn't show'** → Connector activation runs a protected-customer-data probe: fetch one recent order requesting customer/email/phone/addresses; if the response is HTTP 200 with null fields plus an errors entry like 'This app is not approved to access the Customer object', mark connection.health.customer_data='permission_denied' and show the exact Dev Dashboard action. - **Candidate storage shape** → One table order_import_candidates (org_id, connection_id, source_order_id, source_updated_at, inbound_delivery_id, status hydrating|blocked|promoted|superseded|discarded, normalized jsonb (zod CandidateOrder), sections jsonb (11 sections × status vocabulary), blockers jsonb, api_version, connector_version, promoted_order_id, attempts, last_error, timestamps) UNIQUE(connection_id, source_order_id, source_updated_at). No candidate line table: the Import-blocked screen renders lines from normalized jsonb through the same OrderView DTO as promoted orders.  
  _A blocked candidate must show 'three bottles of serum at this price' without entering fulfillment; a jsonb snapshot does that with one table and zero joins. Promotion is a projection of the same shape into canonical rows, so there is one normalizer and one renderer._ [my_call] — astra B steps 3-6; ponytail ladder rung 1 (no second table until a query needs it)
- **Section-status vocabulary storage** → Fixed set of 11 sections (identity, items, buyer, addresses, price, currency, payment, fulfillment, returns, context, evidence) and 5 statuses (loaded | not_applicable | not_exposed_by_provider | permission_denied | fetch_failed) defined once in packages/domain (new packages/domain/src/orders/candidate.ts) as zod enums; stored as jsonb on the candidate and copied onto orders.sections at promotion together with orders.source_synced_at. Never a boolean complete flag.  
  _An empty refunds list after a successful fetch is 'no refunds'; a failed fetch is not. The UI must show which, per section, and the dashboard must count blocked imports separately._ [all_agree] — astra B 'Do not treat every empty field alike'
- **Completeness rules (S1, Shopify)** → validateCandidate() is a pure function returning {sections, blockers}. Blockers (each with code + next_action): R1 hydrate_failed (transport/top-level errors on required paths) → retry via outbox, then blocked; R2 pagination_incomplete (any hasNextPage left true); R3 line_lost (normalized line count ≠ source line count, or qty ≤0, or unparseable money); R4 totals_mismatch (Σ line discountedTotal + shipping + (tax if !taxesIncluded) − orderDiscounts ≠ totalPriceSet.shopMoney, exact in minor units); R5 unsupported_currency (shop or presentment currency not in SUPPORTED_CURRENCIES); R6 buyer_unavailable (no email AND no phone AND customer null) with status permission_denied if the redaction signature is present else not_exposed_by_provider; R7 shipping_address_missing when any line requiresShipping (else addresses=not_applicable); R8 line_unmapped (no variant_source_links row for (connection, source_variant_id) and line not classified custom_nonstock); R9 dimensions_unresolved (connection has no legal_entity/brand/channel); R10 test_order is NOT a blocker: promote with is_test=true and exclude from posting/reports. Data-complete-but-stock-short is NOT a blocker (that is a reservation shortfall in IN).  
  _Astra separates import completeness from stock readiness, payment readiness and risk holds; SKU-string mapping is explicitly insufficient; missing access must be distinguished from legitimately absent data._ [all_agree] — astra B step 4; astra 'A fully mapped order without sufficient stock is different'
- **Unmapped lines block promotion (do not promote half-mapped orders)** → An order with any unmapped, unclassified line stays a blocked candidate (visible with full line detail) until the resolver maps the source variant, creates the variant from the snapshot, or classifies the line custom_nonstock; then the candidate is reprocessed and promoted. order_items.variant_id stays NOT NULL except when line_kind='custom_nonstock' (CHECK constraint).  
  _Promoting with null variant_id would push null-handling into reservations, costing, posting and courier booking; keeping the kernel invariant and blocking at the door is smaller. The owner still sees the purchased items because the exception screen renders the candidate._ [synthesis_overrides] — astra: 'Unmapped variants should block action, not erase information… Resolution reprocesses the candidate'; kernel keep decision
- **Atomic promotion enforced by the database, not by discipline** → promoteCandidate(tx) runs inside withOrgContext and, in ONE transaction: SELECT candidate FOR UPDATE; version check (candidate.source_updated_at > orders.source_updated_at or no order); upsert orders header (+snapshots), upsert order_items by (order_id, source_line_id), replace order_source_transactions/refunds/fulfillments by source id, findOrCreateCustomer (connection-scoped source customer id first, then suggest-only email/phone match), reservation request (IN), outbox events, candidate.status='promoted', inbound_deliveries.status='processed'. DB guards: orders.accepted_candidate_id NOT NULL when source IS NOT NULL (CHECK); a DEFERRABLE INITIALLY DEFERRED constraint trigger on orders/order_items asserting count(order_items where order_id) = candidates.line_count for the accepted candidate at COMMIT; UNIQUE(connection_id, source_order_id) on orders.  
  _Astra: 'A complete = true flag that arbitrary code can set is insufficient… use database-enforced promotion rules'. A deferred constraint trigger is ~20 lines of plpgsql and makes 'header committed, items later' impossible from any code path, including future agents._ [all_agree] — astra B step 5 and 'The structural guarantee has limits'
- **Variant mapping by connection-scoped source IDs** → New table variant_source_links (org_id, connection_id, source_variant_id, source_product_id, source_inventory_item_id, variant_id FK, sku_snapshot, title_snapshot, state active|deleted, UNIQUE(connection_id, source_variant_id)). Replaces product_variants.shopify_variant_id / shopify_inventory_item_id (org-unique, one store per org). Lookups are by (connection_id, source_variant_id) only; SKU equality is offered as a resolver SUGGESTION, never auto-applied. Outbound catalog push (outboxWorker handleShopifyProductPush) must write this table (CX dependency).  
  _Three brands = three stores = the same SKU string in three catalogs; org-unique Shopify ids cannot represent that; astra: 'a SKU string alone is insufficient'._ [all_agree] — packages/db/src/schema.ts L119-120 (org-unique shopify_variant_id / inventory_item_id indexes); packages/db/src/schema/shopify.ts L24 (one connection per org)
- **Revision handling for updates** → Candidate revision = fetched updatedAt. Promotion of a newer revision diffs by source ids: lines upserted (original quantity kept, current_quantity/unfulfilled/refundable updated), transactions/refunds/fulfillments appended by source id, header money re-snapshotted, previous accepted revision retained (orders.accepted_candidate_id history via candidates rows). If the new revision is BLOCKED (e.g. edit added an unmapped line, or a fetch failed), the accepted revision stays live, orders.pending_revision_candidate_id is set, the workspace shows 'newer source data pending' and fulfillment/refund actions are blocked until resolved. A delivery whose fetched updatedAt ≤ accepted is marked superseded. Per-order serialization: pg_advisory_xact_lock(hashtext(connection_id||source_order_id)) before the FOR UPDATE, so a not-yet-existing order is also serialized.  
  _Astra: 'Never replace good items with an empty array because a later API call failed… Serialize updates per source order or use version checks'._ [all_agree] — astra B step 7 and 'For incomplete updates to an existing order'
- **Incremental scans + scheduled reconciliation are product features** → Every 15 min per active connection: orders(query:"updated_at:>='<cursor − 10 min>'", sortKey:UPDATED_AT, first:250) paginated; any (id, updatedAt) without a candidate → enqueue hydration; cursor = max updatedAt seen, stored on the connection. Daily: per-day ordersCount vs local accepted+blocked for the last 60 days, per-order presence for the last 7 days, totals compare for accepted revisions; findings (missing_locally, revision_behind, totals_differ, blocked_over_24h) into reconciliation_findings shown on the owner home 'Orders needing attention' with blocked imports counted separately. On activation the same scan runs from now−60d (or all history once read_all_orders is granted). bulkOperationRunQuery deferred: at this store size, cursor pagination is enough.  
  _Missed webhooks are certain over time (8 retries/4h then dropped). Reconciliation independent of webhooks is a keep in every review; bulk operations add an async polling state machine for no S1 benefit._ [all_agree] — https://shopify.dev/docs/api/admin-graphql/latest/queries/orders (updated_at filter, UPDATED_AT sortKey); https://shopify.dev/docs/api/usage/access-scopes (read_all_orders: default window is orders created within the last 60 days; request via Partner/Dev Dashboard access request form)

- product_variants.shopify_variant_id / shopify_inventory_item_id as the mapping key — Org-unique, one store per org; replaced by variant_source_links keyed by connection.
- shipment_tracking rows as 'history' on the order page and the bosta|mylerz enum — DM collapses shipment models into one shipments table; the workspace fulfillment section reads that.
- customers.address free-text as the order address source — Orders carry immutable billing/shipping snapshots (jsonb) that survive customer edits and product deletion.
- bulkOperationRunQuery-based reconciliation and Cloudflare Workflows for backfill (synthesis connector-shopify module) — Cursor pagination at 250/page covers this store size; bulk ops add an async job state machine with no S1 payoff. Revisit in S5 if a scan exceeds the cron budget.

- GDPR mandatory webhooks (customers/data_request, customers/redact, shop/redact) — Required only for App Store distribution; this is a custom app. Re-evaluate if distribution changes.
