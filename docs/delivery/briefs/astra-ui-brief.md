# IRTH OS admin — UI architecture, design system, and mobile-first screen program (design-direction brief)

You are the design lead + frontend architect for a rebuild of the admin/control-room UI of IRTH OS. Produce ONE decisive markdown spec (target 3,000–4,500 words plus tables). Read-only sandbox: inspect the repo, read official docs, do NOT write files. Be opinionated; say what you would refuse.

## Product in one paragraph
IRTH OS = one practical control room for an Egyptian consumer-goods group: parent brand IRTH + 3 legally separate brands, ONE operations team. Channels: own storefronts (Shopify + WooCommerce, 3+ domains), WhatsApp/Instagram DM manual orders, a physical shop (web POS, online-only), wholesale B2B, marketplaces later. Money: COD via couriers (dominant), gateways, bank/InstaPay, B2B credit. Inventory: buy-and-resell + in-house manufacturing/packaging with lots/expiry (cosmetics). Full statutory accounting per legal entity + consolidated group. Users: owner/admin (phone-heavy, wants to "never open the Shopify admin again"), accountant (desktop, dense), ops/warehouse/shipping staff (phone/tablet on the floor), POS cashier (tablet), external suppliers (portal: see POs, confirm deliveries). Arabic-first, RTL, with English. Cheapest possible; no paid design/UI SaaS; solo owner directing coding agents (Codex/Jules/Hermes/Claude) in parallel — so the spec must decompose into independent build packets.

## The architecture decision already made (do not re-litigate)
A separate astra review concluded: modular monolith; keep the proven kernel (double-entry ledger, WAC costing, RLS tenancy, outbox/inbox); unit of delivery = one COMPLETE business transaction, starting with the owner's real Shopify order that today shows only "order number + price" (no items, no customer, no address — a facade). Storefront-admin parity contract: for every order the admin shows everything needed to identify the buyer, understand every item, fulfil, explain the money, handle a return, inspect the source; each section carries a status: `loaded` / `not_applicable` / `not_exposed_by_provider` / `permission_denied` / `fetch_failed`; failed imports appear as "Import blocked" with the exact missing section and next action, never as a half-order. Five approval policies + one approvals table. Fixed role templates. Hand-written SQL reports (8): sales/contribution by entity·brand·channel·currency; orders needing attention (incl. blocked imports); stock availability/ageing/expiry/stockouts; funnel by storefront/device/campaign; repeat/cohorts; courier delivery/RTO/COD remittance; fulfilment throughput/turnaround/errors; site speed + integration health. Analytics: first-party pixel → Worker `/collect` → Cloudflare Queue → Postgres partitions.

## What exists (inspect it, then judge keep vs rebuild)
Monorepo: `apps/admin` (Next.js 15 App Router on Vercel, tRPC, Better Auth, Arabic RTL already present in places), `apps/api` (Hono on Cloudflare Workers), `packages/db` (Drizzle + Neon Postgres), `packages/emails` (react-email, Arabic RTL layout). Look at: `apps/admin/package.json`, `apps/admin/src` (app routes, components, styling, i18n/locale handling, data-fetching pattern, existing dashboard/stat components, tables, forms), tailwind/postcss/globals CSS, any `components/ui` (shadcn?) folder, the current orders list and order detail pages, and `apps/mobile` (Expo — the plan deletes it; note anything worth salvaging as a PWA pattern). Report concretely: what is reusable, what is a dead end, and why.

Brand context (storefront brand bible — NOT to be copied literally into the admin): CALM · REFINED · TIMELESS; ivory #F3EFE7 / black #111111 / gold ≈#B0885E; Canela + Suisse Intl on the storefront. The admin is a working tool used 8h/day — it should feel like it belongs to the same house (restraint, warmth, precision) without pretending to be the storefront.
